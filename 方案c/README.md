# 方案 B 检查结果与方案 C 设计

## 结论

当前证据不支持把方案 B 持平直接归因于“LoRA 没挂上”或“JEV 前向写错”。实际保存的适配器存在非零更新，小型 Qwen3 上的梯度、因果读出、收益公式、保存重载检查均通过。更值得优先处理的是：**路由输入缺少候选视频内容，训练与测试的候选图库和反事实生成协议存在差异，而开发集上的胜出只涉及两条查询。**

这里的 50.60% 是“粗排分差决定哪些查询做深度验证”的结果。原始粗排测试 R@1 是 **39.60%**。方案 B 已比原始粗排提高 11.00 个百分点，但没有超过同预算的分差路由。

建议方案 C 保留 B 的收益与风险分解，加入可在推理时获得的候选内容证据，并采用预测头预热和分组学习率。先修正数据接入与协议，再判断更换读出结构是否带来收益。本文中的方案 C 尚未完成训练，下面的 oracle 数值仅用于判断剩余空间。

## 已核实的实验事实

来源是 `outputs/stage2_clip4clip_qwen3vl8b/` 中的原始标注、light/deep 逐查询结果、方案 B 报告，以及本目录的复核脚本。

| 设置 | 测试 R@1 | 有害翻转 | VLM 调用每查询 | 性质 |
|---|---:|---:|---:|---|
| 原始粗排 | 39.60% | 0 | 0 | 已保存结果 |
| 全部执行 light | 45.70% | 20 | 5.000 | 已保存结果 |
| 全部执行 deep | 50.30% | 27 | 31.792 | 已保存结果 |
| 分差路由 | 50.60% | 24 | 27.824 | 同预算基线 |
| 方案 B | 50.60% | 24 | 27.824 | 已保存结果 |
| 仅用分差的条件逻辑回归 | 50.50% | 24 | 27.824 | 本次 CPU 诊断，不是方案 C 成绩 |
| accept/deep oracle，保持基线各成本组 deep 数量 | 52.90% | 1 | 27.824 | 使用真实结果选择路径的上限 |

56.10% 对应 561 条查询在现有三条路径中至少有一条能把正确视频排到第一。精确预算分配也能达到这个并集上限。它说明当前缓存中存在提升空间，不表示模型能自动达到该成绩。

进一步拆分可见：有 **31 条**查询只有 light 能纠正，accept 和 deep 都错误；deep 造成的 27 次有害翻转中，有 **24 次**在 light 下能保持正确。因此方案 C 应同时学习“何时保持粗排”和“何时 light 比 deep 更合适”。单纯增加 deep 使用率不解决问题。

方案 B 选择了 875 条 deep、125 条 accept；分差基线为 876 条 deep、124 条 accept。汇总指标接近并不能证明两者逐查询路由一致。原方案 B 报告没有保存逐查询动作和概率，本次没有对真实 4B 模型重新进行完整推理，不能宣称它们选择了完全相同的查询。

### B 为什么容易学出接近分差的排序

实现位置：[`FactorizedGainHead`](../scripts/13_stage2_router_experiment.py#L152)、[`gain_utility`](../scripts/13_stage2_router_experiment.py#L226)。

令 `p=P(粗排正确)`，`f_a=P(路径 a 正确 | 粗排错误)`，`s_a=P(路径 a 正确 | 粗排正确)`。B 的效用是：

```text
u_a = (1-p) × f_a - λ × p × (1-s_a)
```

当 `λ=1`，它恰好等于“路径 a 的正确概率减去粗排正确概率”，公式本身正确。但若输入无法区分具体候选，`f_a`、`s_a` 容易接近总体统计。此时效用主要随 `p` 变化，而 `p` 又由分差先验强烈驱动；在相同验证成本下，排序就可能接近小分差优先。

这是结构上的可能机制，尚未通过真实 4B 的逐查询概率或隐藏状态消融证实。CPU 诊断中，只用分差的条件逻辑回归已达到开发集 32.98%、测试集 50.50%，与 B 的开发集 32.98%、测试集 50.60% 接近，说明当前成绩不需要复杂的文本表示也能接近。

## 更可能限制效果的因素

### 输入没有提供区分候选所需的内容

[`build_state`](../cvr/router.py#L39) 只提供查询、查询长度、Top-5 分数、分差、Top-10 熵和最大概率。候选视频帧、视频特征、候选间的内容差异都没有进入模型。

所以即使 Qwen3 理解了“护士洗手后清洁表面”的语义，它仍不知道当前前两名视频分别包含什么，无法直接判断深度验证是否会误伤该查询。LoRA 和更多同格式数据可能改善统计拟合，但不会自动补上候选证据。

### 训练与测试的图库难度不同

[`02_retrieve.py`](../scripts/02_retrieve.py#L32) 分别使用各 split 的全部视频作为图库。实际训练矩阵为 `9000×9000`，测试矩阵为 `1000×1000`。

| 子集 | 查询数 | 原始粗排 R@1 | Top-1 与 Top-2 分差中位数 | Top-1 分数均值 |
|---|---:|---:|---:|---:|
| train | 2123 | 22.66% | 1.038 | 33.111 |
| dev | 285 | 24.21% | 1.191 | 33.167 |
| calib | 592 | 23.65% | 0.980 | 33.253 |
| test | 1000 | 39.60% | 1.928 | 30.571 |

用现有训练相似度矩阵，为原 3000 条查询各保留 GT 并随机抽取 999 个训练视频作为负候选，三个固定随机种子的粗排 R@1 为 **49.23%、50.87%、49.80%**。这个检索诊断表明图库规模会明显改变任务分布；训练内容本身也与测试内容存在差异，统一图库规模不能保证全部差异消失。

缩小图库会改变候选和验证结果，**不能直接沿用旧的 light/deep 标签**。若采用与测试匹配的图库构造，必须重新执行对应候选的验证并保存新标签。

### 训练和测试的 deep 不是完全相同的生成协议

训练标注在 [`stage_llm`](../scripts/05_build_router_data.py#L55) 中先参考已知错误视频的人工 caption，产生 `label_fragile`，再用该类型生成反事实。

当前测试回放读取的是 `test_deep_prompt.jsonl`。它由 `10_run_pipeline.py --mode deep` 生成，此时 [`fragile` 固定为 `auto`](../scripts/10_run_pipeline.py#L60)。方案 B 的测试回放并没有使用自己预测的 fragile 去重新生成反事实。

这意味着 B 学习的是“按标注类型生成反事实后的 deep 收益”，测试使用的是“按 auto 生成后的 deep 收益”。fragile 辅助任务在这张回放成绩表中也没有直接驱动验证路径。该差异确实存在，影响大小需要统一协议后比较，不能仅凭代码断定它解释了全部损失。

### 风险样本少，开发集选择的优势也很小

原 3000 条标注实际划分为 train 2123、dev 285、calib 592。train 中 light 有害翻转 41 条、deep 有害翻转 56 条；在 481 条粗排正确样本中，两者分别占 8.52% 和 11.64%。

B 使用条件 BCE，并非 A 的“不变、纠正、有害”三类 CE，因此不能把 A 的多数类问题原样归因给 B。但 B 仍需要从有限风险样本中学到可泛化的条件规律。

B 在 dev 上从 92 条正确提升至 94 条正确，有害翻转均为 4 条。只多两条查询，开发集胜出不足以证明稳定泛化。已有数值特征诊断中，更复杂的逻辑回归和小型树模型也没有在 dev 上稳定超过仅分差模型。

### 新预测头和 LoRA 直接使用同一优化设置

[`train_gain`](../scripts/13_stage2_router_experiment.py#L231) 从基础 Qwen3 重新初始化 LoRA 和随机收益头，使用同一个 `1e-4` 学习率同时训练，并叠加权重 0.5 的 fragile 损失。没有收益头预热，也没有主干与头的学习率分组。

这不是已证实的实现错误，但随机头尚未稳定时就同时改变主干，是值得单独消融的训练选择。fragile 标签依赖候选 caption，而输入没有候选内容，辅助任务是否帮助路由也应通过权重 0 与 0.5 的对照确认。

### 9000 条数据的接入需要单独确认

扩充脚本将数据写入 `outputs/stage2_clip4clip_qwen3vl8b/router_data_9000/`。但 [`13_stage2_router_experiment.py:377`](../scripts/13_stage2_router_experiment.py#L377) 和 [`06_train_router.py`](../scripts/06_train_router.py#L19) 都仍读取 `router_data/router_data.jsonl`。

**扩充完成后直接执行原训练入口，仍会读取旧数据。** 只覆盖 `router.n_train_queries=9000` 也不会改变这两个训练入口的数据源。后续应增加可选的 `--router-data` 参数，并将实际路径、文件哈希、split 数量写入报告；保留原默认路径以便复现 B。

按当前扩充逻辑，6000 条新增样本全部进入 train，完成后的总量应为 **train 8123、dev 285、calib 592**。9000 是标注总量，不是训练 split 的样本数。本次不修改或重启正在准备的数据流程。

## 推荐的方案 C

### 用候选内容证据预测路径收益

保留三个动作和 B 的五个概率 logits：粗排正确性一个，light/deep 在粗排错误或正确条件下的成功概率各两个。改变输入与优化方式，先保持概率定义不变，便于判断收益来自哪里。

```text
查询文本 ── Qwen3 表示 ─────────────────────────────┐
查询文本 ── 冻结 CLIP4Clip 文本特征 ─┐              │
Top-K 视频 ─ 冻结 CLIP4Clip 视频特征 ─┴─ 候选比较 ─┼─ 收益与风险头
原始分数统计 ── 数值分支 ───────────────────────────┘
                         ↓
              accept / light / deep 预算分配
```

具体设计建议如下，均为待验证的实现选择：

1. 使用同一冻结检索器产生的查询和候选特征。候选至少覆盖 deep 的 Top-16，同时标明 light 覆盖的 Top-5；为视频保留池化表示，第一轮不增加逐帧时序模块。
2. 借鉴 VideoJev 的查询与候选双投影及 cosine 打分，构造候选聚合表示。额外保留 Top-1 与其他候选的表示差异、查询与候选逐维交互以及候选排名信息，让头有机会区分“分数接近但语义不同”的情况。
3. Qwen3 的查询表示作为文本补充，与数值分支、候选证据分支拼接后，用小型 MLP 输出 B 的五个 logits。分差先验保留为可单独关闭的残差基线，避免同时更换标签定义和全部模型结构。
4. 第一阶段冻结 Qwen3 与视觉编码器，只训练投影、聚合层和收益头。固定表示可缓存。第二阶段再决定是否打开 Qwen3 LoRA；如果打开后 dev 没有收益，就保留冻结版本。
5. 初始对照可采用头预热学习率 `3e-4`；联合训练时 LoRA `2e-5`、头 `1e-4`。这些是实验起点，不是已验证的最优超参数。先做无 fragile 辅助损失版本，再单独比较原来的 0.5 权重。

现有相似度矩阵只有标量分数，**不能从中恢复视频特征**。`temp/stage0_clip4clip.py` 已能加载实际检索器并编码文本、视频，但当前只保存相似度矩阵。方案 C 需要另行导出带 video ID、query ID、权重哈希和归一化协议的冻结特征缓存。

这些候选特征不使用测试人工 caption、GT 视频标识、GT rank 或已有 VLM 的结果。后几项可以作为训练监督和离线评估依据，不能进入决策输入。特征提取和路由模型自身的耗时也要统计；VLM 调用相同不代表总计算成本相同。

### 统一标签中的路径含义

先固定 deep 为 `fragile=auto`，让训练标注与当前测试缓存的生成协议一致。若之后恢复预测 fragile，训练标签也应由训练内交叉拟合得到的 fragile 预测生成，再评估完整链路。

针对图库差异，先在训练视频内部构造包含 GT 的固定 1000 视频图库，按视频划分查询监督集合。用一个独立 pilot 比较与原 9000 图库的收益概率分布，再决定是否批量重标注。构造好候选后重新执行 light/deep，不能用改候选前的标签拼接成新训练集。

第一轮仍使用不加权的条件 BCE，分别报告纠正和有害概率的校准情况。若使用稀有风险样本重采样，验证与校准必须回到自然比例；经过类别加权的分数不能直接当作自然风险概率。

### 把选择模型和分配预算分开检查

保持当前 **精确相同 27824 次 VLM 调用**作为主对照，便于与 A/B 比较。补充报告“不超过相同预算”的结果，观察是否存在为了花完预算而进行负收益验证的情况；两种预算设置分别标注，不能混为同一实验。

开发集用于预先选定结构、轮次和风险权重，校准集用于固定概率校准及阈值。最终测试时保存每条查询的五个 logits、各动作效用、预测成本、实际动作，以及与分差基线的差异。测试集标签只用于评估，不用于选结构、阈值或轮次。

## 实验顺序和判断标准

| 顺序 | 对照 | 主要回答的问题 |
|---|---|---|
| 1 | 原 B，明确指定扩充数据文件 | 9000 总标注是否真正进入训练，train 是否为 8123 |
| 2 | B 加头预热和分组学习率，输入不变 | 训练设置本身是否限制了收益头 |
| 3 | 在相同标签上加入冻结候选特征 | 候选内容是否提供分差之外的增益 |
| 4 | 统一 auto 协议，再比较是否重构图库 | 标签协议与图库差异各影响多少 |
| 5 | 最佳候选模型比较冻结 Qwen3 与 LoRA | 文本主干微调是否仍有额外贡献 |
| 6 | 最后单独比较 fragile 辅助损失和读出位置 | 辅助任务及特殊读出是否值得保留 |

每个实验使用独立目录，保留输入文件路径与哈希。不要将候选特征、图库、生成协议、头结构和损失在同一轮全部改掉，否则无法判断真正有效的修改。

沿用现有目标：同预算下 R@1 高于分差基线，同时有害翻转不高于基线。开发集上的小幅胜出应通过预先固定的多个训练种子或训练内划分复核；最终测试报告配对差异和不确定性，不能把一两条查询的波动直接解释为稳定提升。R@5、R@10 继续沿用项目现有统计。

## 本目录的复核材料

- `audit_data.py`：复现分差基线、分配器穷举检查、训练与测试分布、oracle 上限、少量 CPU 特征诊断及训练图库重采样。
- `audit_results.json`：上述计算结果，含主要输入文件的 SHA256。CPU 模型只用原 train 拟合、dev 选择；测试检查固定分差模型与 dev 选出的模型，本次两者相同。
- `check_model.py`：调用现有模型构建、读出和收益头代码，检查真实 tokenizer、小模型梯度、适配器保存重载以及真实 4B 适配器张量。
- `model_checks.json`：模型检查结果与依赖版本。

```bash
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python -B 方案c/audit_data.py

PYTHONPATH=data/models/router-python-deps OMP_NUM_THREADS=2 \
  /home/omnisky/miniconda3/envs/chart-vllm/bin/python -B 方案c/check_model.py
```

本次新增内容均位于 `方案c/`，没有改写原 B 的训练入口、权重、配置或扩充标注。
